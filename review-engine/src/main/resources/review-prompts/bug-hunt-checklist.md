- Failure disposition: each error cause the change can raise or catch, and whether it is handled correctly. A deterministic failure (validation, not-found, permission, malformed input) must not be retried as if transient, and a transient one (timeout, throttling, unavailable) must not be treated as permanent. Check that a wrapped exception is unwrapped the same way at every handler.
- Errors classified by message text: a new or changed check that decides what kind of error occurred by searching the error's message or string form (a substring such as "NOT_FOUND", "timeout", or "denied") instead of a structured status code, error type, or field from the operation itself. An error from another layer (transport, registry, gateway, an unrelated downstream entity) that mentions the same word is then misclassified. Report it when the classification drives a user-facing claim, a retry decision, or hides a fault. Name the other source that can produce the text, and tell the author to match only the structured status from the operation being classified.
- Swallowed failures: a catch that only logs or ignores the error, or an error path that returns a success-like value (empty list, null, default, true, OK status), so the caller cannot tell the operation failed. Also check functions that collapse upstream, parse, or projection failures into a coarse error status (such as unavailable or fallback) while the caller logs that outcome only at DEBUG or not at all: when some failure branches log WARN or ERROR and sibling branches (empty response, invalid JSON, missing field, schema or projection error) return the same status silently, production loses all signal on those failures. Report each silent branch and tell the author to log a WARN with a fixed reason token (never raw payloads or user input).
- Error-channel bypass: a method whose callers expect failure as a returned value (an Either, Result, or Try left; a failed future; an error status or code) that can instead throw from inside a continuation or mapper (thenApply, thenCompose, map, flatMap, then, a stream lambda). Typical throws are a parse of downstream data, orElseThrow, a precondition or cast, or a getter on a required field the request may not have fetched (a projection, field mask, or partial response). Read how the rest of the class reports errors; when it uses the returned value, the throw escapes it, often wrapped (CompletionException, ExecutionException), and skips the callers' error mapping. Tell the author to return the error value instead, naming the method that throws and the path it is reached from.
- Incomplete fail-closed validation: code that turns some malformed input (bad JSON, a wrong top-level type) into a safe error value, then passes the payload to parsing or conversion code that can still raise on nested data, with no handler around that call. Typical raises are iterating a truthy non-list behind "x or []" or a default, an index or key into a missing or wrong-typed field, a numeric or timestamp conversion with no range check, and a cast. Trace each nested field the helpers read to a check or a handler; when one raises and the callers re-raise, the safe error value is skipped and the whole request fails. Name the field and the input that raises, and tell the author to catch those errors around the call and return the same error value, or to check the nested types.
- Abandoned blocking work: a timeout applied to the caller's future (completeOnTimeout, orTimeout, Promise.race, a select on a timer) around a blocking or remote call that the timeout does not cancel or interrupt. The caller gets its fallback, but the call keeps running until its own deadline and holds its thread. When that thread comes from a small or shared executor, slow calls fill the pool and queue and stall or reject unrelated work on it. Name the executor's size and its other users, and tell the author to give the call a deadline no longer than the timeout or run it on a separate executor.
- Fail-open decisions: an authentication, authorization, quota, rate-limit, signature, or entitlement check that allows the action when the check throws, times out, or returns null or an unrecognized value. Such checks must deny on error.
- Partial failure: a multi-step change (two writes, a write plus a message, a file plus a database row) with no transaction, rollback, or compensation when a later step fails; or a message, email, or remote call sent inside a transaction that can still roll back, where an outbox or after-commit hook belongs.
- Silently discarded records: a filter, skip, or continue that drops malformed or incomplete input rows (missing required fields, failed parse) while still returning success, with no count, metric, or log of what was dropped. Callers see fewer results with no signal. Tell the author to count the dropped rows and emit one aggregated WARN (or metric) with the count, not a log line per row. When an empty or shorter result is itself read as a definite answer (nothing failed, nothing is owed, no match exists), counting is not enough: tell the author to fail closed on a malformed entry and return the same error value the code uses for other malformed input.
- Removed safeguards: a deleted or weakened guard, null check, validation, authorization check, lock, cleanup, or required call. Read the '-' lines, not only the '+' lines.
- Incomplete guard exemptions: a new or widened exemption, allow-list branch, or early-return carve-out that skips a guard, validation, policy check, or fallback response. Trace three things: (1) every representation of an exit or action that reaches the guard (for example, a direct return or no-tool finish with an empty action list alongside a terminal tool or action, or streaming alongside non-streaming) — rejecting disallowed actions only when an action list is non-empty lets an empty-list final answer slip through unverified; (2) whether a post-step branch checks only that the prior step (a lookup, verification, or authorization) was called while ignoring its result or observation, so an error, empty, not-found, invalid-input, or unavailable outcome still unlocks unrestricted output; and (3) when a pre-step branch uses a regex or keyword heuristic on free-form text (such as absence of a currency figure plus common words like `date`, `when`, `year`, `link`, or `url`) to allow a clarification prompt, whether a declarative unverified claim containing one of those words and no figure (for example, "There were no charges on that date") also passes. Report any reachable bypass as an "issue", name the input or step outcome that slips past the guard, and tell the author to require a verified success result from the prior step and limit the pre-step exemption to asking for missing input with no factual claim.
- Unchecked absent inputs: for every changed line that reads a protobuf or other optional field (getX() on a message, an Optional, a nullable column), check that the code proves the field is present first. A protobuf scalar or string read without its has*() check, or reached by an else branch after other has*() checks failed, returns a default ("", 0, false). When that default is used as a lookup key, identifier, or filter, the code silently queries for the default instead of rejecting the input. Flag the read and tell the author to check presence and non-blankness first.
- Internal input limits: code that trusts a generated or internal input (a config or feature file, a metadata or system-table query, a cache entry, another service's response) to stay within a size limit, hold no duplicates, or have no blank fields, and fails hard when it does not (an unchecked exception, panic, unwrap, assertion, or fixed-size buffer) instead of rejecting the bad input and keeping the last good state. A query that can start returning duplicate or extra rows, such as one missing a schema, tenant, or version filter, counts too.
- Mixed versions: a changed serialized, persisted, cached, or queued shape (field, enum constant, config key, event type) that an older reader or writer still running during a rolling deploy, or data written before the deploy, will reject or misread.
- Outbound calls: a new network, RPC, database, or file call with no timeout, or with retries that are unbounded or not idempotent-safe. A retry, reconnect, or restart loop also needs exponential backoff with jitter and a cap: fixed or immediate retries from many clients overload a dependency while it recovers.
- Downstream identity and result completeness: for each new or changed remote read, including a new caller of an unchanged helper, trace the outgoing request through shared wrappers, graph resolvers, decorators, and secondary fetches to the downstream implementation or contract. Check which member/user identity, tenant, delegation, scope, or operation-specific access-use-case context each hop requires and what the wrapper actually forwards; an application viewer is not automatically equivalent to the end-user identity or an authorized delegated read. If local source is insufficient, use only the permitted read-only MCP source/contract lookup described in the evidence policy, even when local callers already exist. Establish whether missing or incorrect context causes an error, permission-filtered empty/partial data, or omitted decorated fields, then trace how the new caller maps that result: empty or filtered data is not proof of nonexistence, no access, or a complete result. Report only a contract-backed mismatch for a supported caller identity with a concrete changed-line failure path; cite both the downstream requirement and the local request/result mapping. This is a correctness check, not limited to changed API signatures or missing external callers. Do not infer a requirement merely from an available context field, copied tests, an empty fixture, or a failed lookup. Distinguish an authoritative not-found result from authorization filtering, missing ingestion, and transport failure; do not claim which one occurred without evidence. Never recommend blanket elevation or bypassing authorization: confirm the specific operation permits the proposed context/use case and preserve the inbound caller authorization and tenant boundary. If the required contract or safe context propagation cannot be confirmed, omit the finding or the unverified fix rather than inventing one.
- Data changes: a schema migration without the backfill or default existing rows need, or a new query filtering or joining on a column with no index.
- Unstable pagination: offset/limit paging whose sort key is not unique across the filtered rows — including ordering only by columns the filter pins to a single value. Tied rows can reorder between page requests, so pages skip or duplicate rows. A key that looks unique is not when some rows hold null or a shared placeholder ("missing", "unknown", 0) in it; check how each sort column is filled, including in other changed files. Paging queries written in documentation or runbooks count too. Tell the author to add a unique tie-breaker (such as the primary key) or switch to cursor-based paging.
- Nondeterministic pick: a new or changed choice of one row or value from several (row_number() or rank() kept at 1, LIMIT 1 or TOP 1 after ORDER BY, first(), max_by/min_by, arbitrary() or any_value(), sort then take the first, keep-first deduplication) whose ordering can tie, or that has no ordering at all. Ties include equal timestamps and nulls in the sort key. When the tied candidates differ in the columns used afterwards, the same input can produce a different result on each run, and an audit, report, or reconciliation stops being reproducible. Name the tied columns and what differs between the candidates, and tell the author to end the ordering with a unique tie-breaker (a primary key or request id) or to pick with an explicit rule. Do not report it when a unique constraint or the grouping already makes the candidates identical in what is used.
- Offset paging over a changing set: offset/limit paging across several requests over rows that can be added, removed, or move in or out of the filter between requests (for example, a state filter on records whose state changes). Every change before the current offset shifts later rows, so pages skip or repeat rows; deduplicating catches repeats but not skips. Before recommending a fix, check what the downstream API supports: a cursor or page token, a sort parameter, a sort with a unique tie-breaker, or a filter on a stable key such as id or creation time for keyset paging. Recommend cursor or keyset paging only when the API supports it with a stable, unique order, and name the parameter. Otherwise recommend reading in one request when the set is bounded, re-reading until two passes agree, or marking the result possibly incomplete, and say the API lacks a stable cursor.
- Short page as end of data: a paging loop that stops when a page returns fewer results than the page size, or returns none, while the source can return fewer than requested before the data ends (the server filters or drops rows after applying the limit, caps the page size below the request, or the code filters or maps a page before counting it). Every row of a page can be dropped, so an empty page is no more proof of the end than a short one. The loop stops early, later rows are never read, and nothing marks the result as incomplete. Check comments and the client's contract for such filtering. The end is proven only by a reported total, a next-page token, or the count of rows before filtering falling below the requested size. Without one of those, tell the author to keep paging up to a bound and mark the result incomplete when paging stops before the end is proven.
- Stated data anomalies: when <pr_description>, <commits>, code comments, or test fixtures say real data breaks an expected invariant (one timestamp earlier than another, a field that can be missing or zero, IDs that repeat or are not ordered), find every changed line that reads those fields and check its logic still holds for the anomalous record. For example, an idle or staleness check that reads one timestamp as the last activity misfires when a sibling timestamp can be later; use the later of the two. Quote the statement in "rationale".
- Scoped identifiers: a comparison, sort, tie-break, deduplication, or newest/oldest choice that orders or matches values by an identifier that is unique or increasing only within a scope (one part of a composite key or URN, a per-tenant, per-parent, or per-shard sequence) while the compared values can come from different scopes. Check where the inputs come from; when they can span scopes, the identifier does not establish order or identity. Tell the author to compare the full key or to use a field that is ordered across scopes.
- Inconsistent acceptance: a new or changed parser, normalizer, filter, or validator for a field or identifier (an entity ID, URN, email, date, enum value, or tool argument). Grep the working directory for the field's name and find two kinds of code: other validators, regexes, schemas, and argument or type descriptions; and the consumers that receive the value after the check, such as conversion or parse calls (int(), Long.parseLong, UUID.fromString, an enum lookup) and the tools or handlers that read the field. Compare what each one accepts against the field's current domain contract; being parseable does not establish that a value is valid or authorized. When the new check rejects a form the current contract permits (a URN or other prefixed form, a sign, surrounding whitespace, letter case, a numeric string versus a number), valid input is dropped or refused; when it accepts a form a consumer cannot parse, bad input gets through and fails later. When the check accepts several forms but a consumer needs one, tell the author to convert the value to that form in the check rather than only widening what it accepts. Cite the other definition's or consumer's path in "rationale". A test in the same PR that asserts the narrower or wider behavior does not show it is intended.
- Challenge restrictive invariants: for each new or changed guard or filter that assumes a value range, sign, sentinel, format, uniqueness, or ordering, state the assumption and look for a counterexample in the current domain contract. Trace the field to its authoritative definition, producers, and downstream consumers, including shared validation helpers and migration fixtures or documentation in the worktree. Check supplied <file_history> and <commits> for contract-evolution clues, then confirm them against current code or contract evidence; commit summaries alone are not proof, and a newly added file may have no history. Agreement among copied sibling guards or new tests is not independent proof that the assumption still holds. For example, a comment reserving zero does not justify rejecting every negative ID with `id <= 0`; establish whether negative IDs are legitimate from the producer or current contract, not merely from a signed numeric type or a parser accepting them. If local evidence is insufficient, use only a relevant read-only cross-repo search MCP tool explicitly exposed and permitted by this session's evidence policy; never assume one exists or attempt shell, network, or unavailable history tools. Report only when a concrete value or value class permitted by the current contract reaches the changed guard and is incorrectly rejected or discarded. Cite the contract source and the failing path in "rationale"; if no counterexample is supported, omit the finding. Preserve required sentinel, authorization, and malformed-input checks when recommending a narrower guard.
- Inconsistent classification: a new or changed equality or membership test on an enum, status, or state field that decides what a value counts as (submitted, billed, active, terminal, complete). Search the diff and the working directory for other tests of the same field that decide the same concept: a constant set of states, a switch, a helper predicate, or a filter feeding a total. When the two accept different values (one checks == SUBMITTED while a shared set counts SUBMITTED and ADJUSTED), a value in only one of them is counted by one output and not the other, and results built from both contradict each other. Check the field's documented meaning to decide which set is right, cite the other predicate's path in "rationale", and tell the author to reuse the shared set or predicate. Report it only when both predicates mean the same concept, not when they deliberately distinguish states.
- Closed-world state sets: a new or changed membership test that lists the states that still need action (unpaid, failed, pending, open) and treats every other value as resolved. A missing, unknown, or newly added state then falls into the branch that tells the user or caller nothing is owed, nothing failed, or nothing needs doing. Check how the replaced code or prompt handled a missing value: when it treated the value as actionable, or the change says unknown values must be reported as unknown, report the set and tell the author to list the known resolved states instead, so any other value stays possibly actionable or is reported as unknown. Report it only when the resolved branch produces a user-facing claim or a decision, not display grouping.
- State and ordering: a new state transition the existing state machine forbids, a related field left stale by a partial update, a cache not invalidated, or a cancellation, retry, or await path that leaves work half-done.
- Stale decisions: a check (existence, version, ownership, balance, quota) made earlier and acted on later without re-validating at the write, where a conditional update, compare-and-set, version column, or fencing token belongs; or cleanup that can delete state another worker or a newer version still uses.
- Unguarded rollout: when the repository gates comparable changes behind a feature flag or kill switch, a change that alters behavior for every request or user at once without one. Report it as a "suggestion" that names the flag mechanism it bypasses. When this pull request itself gates a feature behind a flag, toggle, or registered capability or tool, any companion edit (to a shared prompt, allow-list, guard, validator, or default) that still changes live behavior with that gate off and that capability absent is an "issue" naming the gate and quoting any flag-off claim or <repo_guidelines> rule.
- Library contracts: for each standard-library or third-party call the change relies on, check its documented behavior against the usage: what it returns on absence or failure, what it throws, its defaults (timeouts, encoding, time zone, locale, rounding), whether it is thread-safe, and whether a returned collection is a copy, immutable, or a live view.
- Placeholder logic: a stub, hard-coded return value, empty body, or TODO shipped as the implementation of the behavior the pull request describes, or production code that branches on test-only values, test environment variables, or fixture data.
