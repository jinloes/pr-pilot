- Sensitive logging: a log statement that writes personal data (email addresses, names, phone numbers), credentials or tokens, or a whole request, response, payload, or body. Report type "issue", category "security", severity "major" for credentials and "minor" otherwise; tell the author to log a non-reversible identifier instead.
- Hot-path logging: an INFO or higher log inside a loop, stream or batch-item callback, or high-frequency path, or once per request on a routine path when the surrounding class and sibling handlers do not log requests at INFO. Before flagging a single per-request or per-RPC entry/exit log (outside a loop), read the other methods in the same file and one or two sibling handlers or services in the same directory: when existing methods follow the same per-request INFO logging pattern, omit it — matching an established service convention is noise, not a finding. Never guess at unseen traffic (such as "likely polled"): cite a loop or a located caller in the worktree. Report type "suggestion", category "performance", severity "minor"; tell the author to demote it to DEBUG or log one aggregate. Do not flag logs on error paths, at startup, or once per batch or job run.
- Failure log without its subject: a WARN or ERROR log on a failure path that does not include the identifier of the request, row, entity, or input that failed (for example an ID, URN, or key already in scope), so the failure cannot be traced. Report type "suggestion", category "maintainability", severity "minor"; name the in-scope identifier to add.
- Exception not attached: a log on a catch or failure path that has the exception in scope but logs only its class name or message (for example getClass().getSimpleName() or getMessage()) or omits it, discarding the stack trace and cause chain. In Python this includes an except block, with or without "as e", whose log.warning or log.error call has no exc_info=True (log.exception attaches it already). Report type "suggestion", category "maintainability", severity "minor"; tell the author to pass the exception as the final logger argument, or exc_info=True in Python.
- Duplicate or uneven failure logging: a failure path where an inner branch or helper logs WARN or ERROR and returns an error status (or rethrows) and the enclosing method logs WARN or ERROR again for the same outcome, emitting two warnings per failure; or the inverse, where the enclosing method logs outcomes only at DEBUG and relies on inner branches to log WARN or ERROR, while some sibling failure branches (empty response, parse failure, missing field, projection error) return that error status with no log at all. Report type "suggestion", category "maintainability", severity "minor": for duplicate warnings, anchor on the redundant outer log and tell the author to demote it to DEBUG once every failure branch logs its own warning; for a silent sibling failure branch, anchor on that return branch and tell the author to log a WARN with a fixed reason token (never raw payloads or user input).
- Comment hygiene: a changed comment, doc comment, or documentation-file passage (README or other Markdown) that narrates history instead of current behavior ("revived from", "previously", "matches the earlier", "as of <date>"); one that records the pull request's own status instead of a lasting contract, such as what is not implemented yet, which tickets or wiring are still pending, or what a later change should add, so it goes stale once the follow-up merges; one that cites a label defined nowhere a later reader can follow, such as an acceptance-criterion, scenario, or review-thread code that appears in no other repository file and is not a ticket key or link; or a TODO with no tracking reference. Do not flag a changelog, release-notes, or roadmap file whose purpose is to track status. Report type "suggestion", category "maintainability", severity "nit"; tell the author to state the current behavior or stable constraints, drop an undefined label or replace it with a link, and keep transient status in the pull request description or tracker.
- Misplaced doc comment: a changed doc comment whose text describes behavior (a read, timeout, retry, side effect, parameter, or return value) that the member it is attached to does not have, typically because it belongs to an adjacent member. Report type "suggestion", category "maintainability", severity "minor"; name the member it actually describes and tell the author to move it there.
- Overstated doc comment: a changed doc comment, on a type, enum value, method, or field, that presents another field, return value, or behavior as always present or always happening ("named by X", "returns X", "includes X") when that member's own doc comment or the code makes it conditional ("set only when", "if any", an optional field populated under conditions, or a branch that can leave it unset). Read the referenced member's comment, including in other changed files, before judging. Clients read the stronger claim and skip the absent case. Report type "suggestion", category "maintainability", severity "minor"; quote the condition and tell the author to qualify the claim, for example with "when available" or the condition itself.
- Broken documentation passage: a changed documentation-file passage, table cell, or comment that stops mid-sentence, ends on a dangling reference ("returns only the caller's"), or describes code in the same change differently from what that code does (which row a query picks, which value wins, when a field is set). Read the code it describes, including other changed files, before judging. Readers treat runbooks and field tables as the contract. Report type "suggestion", category "maintainability", severity "minor"; quote the broken text and give the complete, accurate wording.
- Schema evolution: a removed protobuf field or enum value whose number and name are not both added to a "reserved" statement, or a deleted "reserved" entry, either of which lets a later change reuse the number or name. Report type "issue", category "compatibility", severity "minor". This rule covers only the missing reservation; an actual reuse is a compatibility break, not hygiene.
Report every occurrence, one comment per changed line. An explicit repository rule overrides these defaults, and an established pattern across the surrounding class and sibling files suppresses non-security logging suggestions (never sensitive logging, dropped exception stack traces, inaccurate doc comments, or missing protobuf reservations).
